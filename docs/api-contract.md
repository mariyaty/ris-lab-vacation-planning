# Контракт API

## 1. Общие сведения

Клиентское приложение Vue 3 взаимодействует с сервером ASP.NET Core по HTTP. Данные передаются в формате JSON. Базовый адрес API в локальной разработке: `http://localhost:5000`.

Основной ресурс — `/api/vacation-requests`. Названия путей согласованы с сущностью `VacationRequest`. Сервер проверяет входные данные, существование связанных записей и права пользователя.

## 2. Методы API

| Метод и путь | Назначение | Тело запроса | Успешный ответ | Возможные ошибки |
|---|---|---|---|---|
| `GET /api/vacation-requests` | Получить список заявок | Нет | `200 OK`, массив заявок; пустой список — `[]` | `401`, `403` |
| `GET /api/vacation-requests/{id}` | Получить одну заявку | Нет | `200 OK`, объект заявки | `401`, `403`, `404` |
| `POST /api/vacation-requests` | Создать заявку | `title`, `siteId`, `description` | `201 Created`, созданный объект с `id`, `number`, `status = New` | `400`, `401`, `403`, `404` |
| `PATCH /api/vacation-requests/{id}/assignee` | Назначить ответственного | `assigneeUserId` | `200 OK`, обновлённая заявка | `400`, `401`, `403`, `404`, `409` |
| `PATCH /api/vacation-requests/{id}/status` | Изменить статус | `status` | `200 OK`, обновлённая заявка | `400`, `401`, `403`, `404`, `409` |

`401 Unauthorized` означает, что пользователь не прошёл аутентификацию; `403 Forbidden` — у пользователя нет необходимых прав; `400 Bad Request` — данные не прошли проверку; `404 Not Found` — конкретная запись или связанный объект не найден; `409 Conflict` — действие противоречит текущему состоянию или бизнес-правилам.

## 3. Формат объекта заявки

```json
{
  "id": 17,
  "number": "VR-00017",
  "title": "Планирование отпусков участка связи",
  "description": "Подготовить проект графика отпусков работников участка.",
  "status": "New",
  "siteId": 2,
  "createdByUserId": 5,
  "assigneeUserId": null,
  "createdAt": "2026-10-03T10:30:00"
}
```

Формат номера приведён как пример; фактический алгоритм формирования номера должен быть единообразно реализован на сервере.

## 4. Создание заявки

**Запрос**

```http
POST /api/vacation-requests
Content-Type: application/json
```

```json
{
  "title": "Планирование отпусков участка связи",
  "siteId": 2,
  "description": "Подготовить проект графика отпусков работников участка."
}
```

**Успешный ответ — `201 Created`**

```json
{
  "id": 17,
  "number": "VR-00017",
  "title": "Планирование отпусков участка связи",
  "description": "Подготовить проект графика отпусков работников участка.",
  "status": "New",
  "siteId": 2,
  "createdByUserId": 5,
  "assigneeUserId": null,
  "createdAt": "2026-10-03T10:30:00"
}
```

Клиент не передаёт `id`, `number`, `status`, `createdByUserId`, `assigneeUserId` и `createdAt`. Эти значения формируются сервером. Если поля не прошли проверку или участок не существует, сервер возвращает соответствующую ошибку.

## 5. Получение заявок

### Список

```http
GET /api/vacation-requests
```

Успешный ответ — `200 OK`:

```json
[
  {
    "id": 17,
    "number": "VR-00017",
    "title": "Планирование отпусков участка связи",
    "description": "Подготовить проект графика отпусков работников участка.",
    "status": "New",
    "siteId": 2,
    "createdByUserId": 5,
    "assigneeUserId": null,
    "createdAt": "2026-10-03T10:30:00"
  }
]
```

Если заявок нет, сервер возвращает `200 OK` и пустой массив `[]`, а не `404`.

### Одна заявка

```http
GET /api/vacation-requests/17
```

При наличии записи сервер возвращает `200 OK` и объект заявки. Если заявки с таким `id` нет, возвращается `404 Not Found`.

## 6. Назначение ответственного

**Запрос**

```http
PATCH /api/vacation-requests/17/assignee
Content-Type: application/json
```

```json
{
  "assigneeUserId": 8
}
```

Сервер проверяет, что заявка существует, пользователь с указанным идентификатором существует и имеет роль `Planner`, а текущий пользователь имеет право назначать ответственного. При успехе возвращается `200 OK` и обновлённый объект. Статус заявки при назначении не меняется и остаётся `New`.

## 7. Изменение статуса

**Запрос**

```http
PATCH /api/vacation-requests/17/status
Content-Type: application/json
```

```json
{
  "status": "InProgress"
}
```

Разрешённые коды: `New`, `InProgress`, `Closed`, `Cancelled`. В рамках сценария ЛР1 назначенный `Planner` может перевести свою заявку из `New` в `InProgress`. Для дальнейшей работы предусмотрены завершение (`Closed`) и отмена (`Cancelled`) назначенным ответственным. Сервер не должен разрешать недопустимые переходы и изменение статуса посторонним пользователем; такие попытки отклоняются, например, с `403 Forbidden` или `409 Conflict` в зависимости от причины.

## 8. Принципы API

- Используется ресурсный путь `/api/vacation-requests`, без `/create` в адресе.
- Для назначения и изменения статуса предусмотрены два отдельных `PATCH`.
- `DELETE` не используется: отмена фиксируется статусом `Cancelled`.
- Машинные коды статусов остаются английскими, русские подписи предназначены для интерфейса.
- Сервер является местом проверки прав и бизнес-правил.
