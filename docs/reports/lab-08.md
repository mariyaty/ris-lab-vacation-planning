# Отчёт по лабораторной работе № 8

**Дисциплина:** Технология разработки информационных систем и веб-приложений  
**Тема:** REST API: создание, чтение, назначение ответственного и изменение статуса  
**Выполнила:** Крец Мария Романовна  
**Группа:** ТРИС-1-23  
**Проект:** ИИ-система планирования графика отпусков и расчёта явочной численности для транспортного предприятия (заказ РЖД)

## Цель работы

Реализовать REST API главной сущности проекта — заявки на планирование отпусков. Обеспечить создание и чтение заявок, отдельные операции назначения ответственного и изменения статуса, проверку входных данных и бизнес-правил, а также безопасную обработку неожиданных ошибок.

## Используемые средства

- C# и .NET 8;
- ASP.NET Core Web API;
- Swagger;
- Postman;
- Git и GitHub.

## Исходное состояние проекта

В качестве основы использован репозиторий после ЛР7. Существующий frontend на Vue 3 и структура проекта сохранены. В backend уже были настроены контроллеры, Swagger, служебные маршруты `/health` и `/info`, сервис через Dependency Injection и HTTP-порт `5000`.

## Ход работы

1. Сверены предметная область и контракт API из `docs/api-contract.md`. Главный ресурс лабораторной — `vacation-requests`, то есть заявки на планирование отпусков.
2. Создана модель `VacationRequest` с полями `id`, `number`, `title`, `siteId`, `description`, `status`, `createdByUserId`, `assigneeUserId`, `createdAt`.
3. Созданы DTO для создания заявки, назначения ответственного и изменения статуса. Клиент при создании передаёт только `title`, `siteId` и `description`; системные поля формирует сервер.
4. Реализован `VacationRequestService`. Заявки и счётчик идентификаторов хранятся в памяти процесса.
5. Реализован контроллер `VacationRequestsController` с маршрутами:
   - `POST /api/vacation-requests`;
   - `GET /api/vacation-requests`;
   - `GET /api/vacation-requests/{id}`;
   - `PATCH /api/vacation-requests/{id}/assignee`;
   - `PATCH /api/vacation-requests/{id}/status`.
6. Добавлена проверка длины `title` (5–80 символов), `description` (10–500 символов) и положительного целого `siteId`.
7. Настроены ответы: `201 Created` при создании, `200 OK` при успешном чтении и изменении, `400 Bad Request` при некорректных данных, `404 Not Found` при отсутствии заявки, `409 Conflict` при попытке перевести заявку в `InProgress` без ответственного.
8. Операции назначения и изменения статуса разделены на два разных PATCH. Допустимые статусы: `New`, `InProgress`, `Closed`, `Cancelled`. Маршрут DELETE не добавлялся.
9. Добавлена безопасная обработка непредвиденных ошибок. В ответ клиенту не передаются stack trace, абсолютные пути и внутренние сведения приложения. Ошибки создания логируются краткой строкой с идентификатором участка и типом исключения.
10. Создана коллекция Postman `docs/api-collection/vacation-requests.postman_collection.json` с запросами для успешного создания, проверки `400`, `404`, `409`, назначения ответственного и смены статуса.
11. Обновлены README и контракт API.

## Запуск backend

Из корневой папки репозитория:

```bash
cd backend
dotnet restore
dotnet run
```

Backend запускается по адресу `http://localhost:5000`. Swagger доступен по адресу `http://localhost:5000/swagger`.

## Проверка API в Postman

1. Импортировать `docs/api-collection/vacation-requests.postman_collection.json` в Postman.
2. Проверить переменную коллекции `baseUrl`: `http://localhost:5000`.
3. Запустить запросы по порядку. Первый запрос сохраняет полученный `id` в переменную `requestId`.
4. Убедиться, что тесты Postman проходят:
   - создание — `201`;
   - короткий `title` — `400`;
   - список — `200`;
   - получение несуществующего id — `404`;
   - смена статуса без исполнителя — `409`;
   - назначение исполнителя — `200`;
   - смена статуса после назначения — `200`;
   - неизвестный статус — `400`.

### Доказательства выполнения

Добавить после локального запуска скриншоты:
1. Swagger со всеми пятью маршрутами `/api/vacation-requests`.
2. Ответ POST со статусом `201`, номером `VR-00001` и статусом `New`.
3. Ответ `400` при коротком названии.
4. Ответ `404` для несуществующего id.
5. Ответ `409` при смене статуса без назначенного исполнителя.
6. Успешные ответы двух PATCH после назначения.
7. Строку серверного лога при временно вызванном исключении и безопасный ответ `500`.

## Проверка безопасного ответа 500

Для учебной демонстрации можно временно добавить в метод `Create` сервиса `VacationRequestService` строку:

```csharp
throw new InvalidOperationException("Учебная проверка");
```

После отправки корректного POST в терминале должна появиться запись вида:

```text
CreateVacationRequest failed; siteId=2; error=InvalidOperationException
```

Клиент должен получить `500` и безопасный `ProblemDetails` без stack trace. После проверки обязательно удалить искусственное исключение, пересобрать backend и убедиться, что обычный POST снова возвращает `201`. Искусственный сбой не должен оставаться в итоговом коммите.

## Ограничения

Данные хранятся только в памяти backend. После перезапуска сервера список заявок очищается — для ЛР8 это ожидаемое поведение. PostgreSQL и постоянное хранение в рамках этой лабораторной не подключаются.

Поскольку в текущем учебном backend ещё нет работающих справочников пользователей и участков, в этой реализации проверяется положительное значение `siteId` и `assigneeUserId`, но фактическое существование участка или пользователя и роль `Planner` не проверяются. `createdByUserId` задаётся сервером демонстрационным значением `5`. Эти проверки требуют полноценной авторизации и справочников на следующих этапах.
