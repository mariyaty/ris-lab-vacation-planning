# Отчёт по лабораторной работе № 6

**Дисциплина:** Технология разработки информационных систем и веб-приложений  
**Тема:** Vue 3: клиент API и mock  
**Выполнила:** Крец Мария Романовна  
**Группа:** ТРИС-1-23  
**Проект:** ИИ-система планирования графика отпусков и расчёта явочной численности для транспортного предприятия (заказ РЖД)

## Цель работы

Отделить пользовательский интерфейс от источника данных: реализовать API-модуль с mock- и HTTP-режимами, асинхронную загрузку заявок, отображение состояний интерфейса и безопасную отправку формы без повторного создания записи.

## Используемые средства

- Vue 3;
- JavaScript и встроенный Fetch API;
- Vite;
- Vue Router;
- переменные окружения Vite (`.env`);
- Git и GitHub Codespaces.

## Ход работы

1. Проверена структура проекта после лабораторной работы № 5. Существующие маршруты, компоненты, стили и общий дизайн сохранены.
2. В корневой `.gitignore` добавлены правила исключения файлов окружения и отдельное исключение `!.env.example`, чтобы пример конфигурации оставался доступным для Git.
3. Создан `frontend/.env.example` с адресом будущего API `http://localhost:5000` и параметром включения mock. Локальный `frontend/.env` содержит те же параметры и не должен попадать в Git.
4. Создан `frontend/src/api/mockTickets.js`. Mock хранит учебные заявки, имитирует задержку около 500 мс и возвращает объект с полями `ok`, `status`, `data`. Реализованы успешное получение списка (`200`), создание (`201`), ошибка валидации (`400`) и учебная ошибка сервера (`500`).
5. Создан `frontend/src/api/tickets.js`, который экспортирует `getTickets()` и `createTicket(body)`. При `VITE_USE_MOCK=true` функции используют mock. При `VITE_USE_MOCK=false` выполняются HTTP-запросы через `fetch` к `/api/tickets` на заданном базовом адресе.
6. В API-модуле реализована проверка `response.ok`. HTTP-ошибки получают свойство `status`; отсутствие сетевого ответа остаётся сетевой ошибкой и не подменяется кодом `500`.
7. В `TicketList.vue` добавлена асинхронная загрузка через `onMounted`. Для списка используется одно поле `screen` с четырьмя взаимоисключающими состояниями: `loading`, `empty`, `data`, `error`. Для ошибки предусмотрена кнопка повторной загрузки.
8. В `TicketNew.vue` отправка формы переведена на `createTicket()`. Клиентская проверка полей сохранена. Созданная запись добавляется в общий реактивный список из ответа API; значения `id`, `number` и `status` не генерируются страницей.
9. Для защиты от повторной отправки добавлен флаг `isSubmitting`: в начале обработчика выполняется ранний выход при активной отправке, кнопка блокируется, а флаг сбрасывается в `finally`.
10. Добавлены учебные переключатели для воспроизведения ответов `400` и `500`. Для проверки отсутствия связи mock отключается в `.env`, после чего запрос направляется на неработающий или недоступный адрес API.
11. Добавлены стили состояний загрузки, ошибки, пустого списка и сообщений формы. Внешний вид предыдущих экранов сохранён.

## Проверка работы

Запуск выполняется из каталога `frontend`:

```bash
npm install
npm run dev
```

После изменения `.env` необходимо перезапустить Vite. В режиме mock используется `VITE_USE_MOCK=true`.

| Сценарий | Действия | Ожидаемый результат |
|---|---|---|
| Загрузка | Открыть `/` | Сначала отображается «Загрузка заявок…», затем список |
| Пустой список | Временно вернуть из mock пустой массив | Отображается «Записей пока нет», таблица не показывается |
| Данные | Открыть `/` при стандартном mock | Отображаются две демонстрационные заявки и сводные показатели |
| Ошибка 400 | На `/new` раскрыть учебные сценарии, включить 400, ввести тему `abc` и отправить | Mock возвращает статус 400; форма показывает сообщение «Проверьте поля»; запись не создаётся |
| Ошибка 500 | Включить сценарий 500 и отправить корректно заполненную форму | Отображается отдельное сообщение о внутренней ошибке сервера; кнопка снова становится активной |
| Успешное создание | Отключить сценарии ошибок и отправить корректную форму | Mock возвращает 201 и объект с серверными `id`, `number`, `status`; запись появляется в списке |
| Защита от двойного submit | Во время задержки mock быстро нажать кнопку несколько раз | Кнопка заблокирована, создаётся одна запись |
| Нет связи | Установить `VITE_USE_MOCK=false`, оставить API недоступным на `localhost:5000` и перезапустить Vite | В Network видна неуспешная попытка запроса; интерфейс сообщает об отсутствии связи |
| HTTP 400/500 | В режиме реального `fetch` получить соответствующий HTTP-ответ от backend | Ошибка обрабатывается по `response.status`, а не как сетевая ошибка |

### Проверка Network и доказательства

Для просмотра запросов открыть инструменты разработчика браузера: **Network → Fetch/XHR**. При `VITE_USE_MOCK=true` mock вызывается непосредственно в JavaScript, поэтому HTTP-запрос в Network не появляется. Это ожидаемое поведение; в отчёт следует добавить скриншот кода/результата mock и подписать его «mock без HTTP».

При `VITE_USE_MOCK=false` запросы отправляются через `fetch` на `http://localhost:5000/api/tickets`. Для подтверждения сетевого отказа необходимо приложить скриншот Network с неуспешной попыткой запроса. Также необходимо приложить скриншот успешного создания заявки и хотя бы одного отказа.

**Место для скриншотов:**

1. Успешное создание заявки и её номер в таблице.
2. Ответ 400 или 500 с сообщением в интерфейсе.
3. Network при отключённом mock и отсутствии backend либо скриншот mock-сценария с пояснением «mock без HTTP».

## Вывод

В ходе лабораторной работы интерфейс приложения был отделён от способа получения данных. Создан API-модуль с двумя функциями, поддерживающий mock и реальные HTTP-запросы через Fetch API. Список заявок загружается асинхронно и отображает четыре отдельных состояния. Форма создаёт запись через API, использует объект ответа сервера и защищена от повторной отправки. Реализована раздельная обработка ошибок 400, 500 и отсутствия сетевого соединения. Подключение backend на C# и базы данных в рамках данной лабораторной работы не выполнялось.
